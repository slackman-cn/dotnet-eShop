# Yuxi 功能文档

本文按能力域说明本机浅克隆中 Yuxi 实际提供的功能，以及二次开发者在自己的场景里应当如何定制。分析对象与架构文档相同：默认分支 `main` 上的提交 `47e4e5a6d905584b3ed47c993c8a7aeb47c15f39`（2026-11-18 17:30:36 +0800，Asia/Shanghai）。包版本在 `backend/pyproject.toml` 与 `frontend/package.json` 中仍为 `0.8.0`。官方教程钉的是 git 标签 `v0.8.0`，并且声明 0.8 只面向全新部署。本树是更新的 `main` 提交，Schema 基线以源码 `BUSINESS_SCHEMA_VERSION = 4`、`KNOWLEDGE_SCHEMA_VERSION = 2` 为准，不能把它写成已经打上标签的发行包。本文不重复部署命令，不启动服务，也不写入任何密钥值。

判断标准来自用户对本项目的看法，但只在源码能够支撑的地方展开：Yuxi 的功能大多构成一条不可再随意拆掉的核心闭环，适合沿着登记点做二次开发和场景定制；与那种「先铺开大量企业选配、再按场景勾选」的套件相比，它的可选面更少，而且可选部分在 Compose 和配置里是诚实可见的。下文会同时写出哪些能力构成不可再瘦的内核，哪些 profile 或叠加文件会真正增删运行能力，避免把每一个模块都说成同等必不可少。

## 1. 产品命题：内核、默认开启和真正的开关

从功能角度看，Yuxi 要交付的不是「一个聊天框加上许多可以关闭的企业模块」，而是四件必须同时成立的事。用户要能配置智能体并在多轮会话里执行多步骤任务；要能把资料变成可引用的检索结果并让智能体按需调用；要能在用户、部门和共享范围里管理这些能力；要能在受控的工作目录里读写文件、执行命令并交付可预览的产物。根目录 `README.md` 把这概括为 Cloud Agents + Knowledge RAG，介绍页 `docs/intro/project-overview.md` 也写明：如果只需要一个不带权限和文件操作的单文档聊天页，Yuxi 的能力会偏多。偏多不是因为堆了闲置选配，而是因为这四件事被设计成同一条工作链路。

这条链路在默认部署里是打开的。`.env.template` 与 Compose 都将 `YUXI_KNOWLEDGE_ENABLED` 缺省为 `true`，Milvus、etcd 和 Neo4j 出现在开发与生产编排的默认服务列表中，不必附加 profile。智能体、会话、权限、工作区和沙盒抽象始终存在。首次访问需要初始化超级管理员，之后才能进入 `/agent` 工作台。发现接口 `GET /api/system/discovery` 向 CLI 和外部客户端宣告当前实例的名称、包版本、知识开关和一批 CLI 能力位。这些是产品开箱即用的功能面。

真正会增删运行能力的开关并不多，而且必须说清楚各自切掉或加入的是什么。

`docker-compose.no-knowledge.yml` 是关闭知识运行能力的叠加：它把 `api`、`worker`、`app-init` 的 `YUXI_KNOWLEDGE_ENABLED` 设为 `false`，并把 `milvus`、`etcd`、`graph` 的副本数设为 0。关闭后，知识库、图谱、评估和知识视图的路由不再装配，discovery 里的知识特征与知识类 CLI 能力变为假，worker 不再派发知识作业、也不再跑投影清理定时任务；内置 `knowledge` MCP 的身份保留，但发现和执行按不可用处理；知识工具不再进入可用目录；普通聊天、会话、沙盒和权限保持可用；持久数据保留，以后可以再开回来。这不是热切换，必须重建 API 和 worker。`knowledge_enabled()` 只接受 `true` 或 `false`，非法值会阻止启动。

`--profile container` 启动 Container 沙盒：构建 `sandbox-image` 并运行 `sandbox-runner`。这是官方本地试用和 Makefile 默认路径，适合单租户可信代码，共享宿主内核，默认禁止沙盒联网。不加该 profile、把 `SANDBOX_BACKEND` 设为 `cube` 并提供 Linux/KVM 执行节点时，走持久用户虚拟机。两种后端都必须存在一种，工作目录始终在；它们替换的是隔离模型，不是「要不要文件执行」这项功能本身。

`--profile all` 增加自托管 MinerU 解析服务。没有它，仍然可以使用随 API 安装的 RapidOCR，以及 MinerU 官方云、DeepSeek OCR 和三套 PaddleOCR 云服务。因此 MinerU 自托管是解析方案中较重的一种，不是文档入库功能的前提。

`docker-compose.abridge.yml` 额外接入 aBridge 设备桥，并打开 Yuxi 作为 OIDC 签发端的相关配置。企业 OIDC 登录默认 `OIDC_ENABLED=false`。Langfuse、网络搜索与抓取、用量统计网关签名，都要额外配置才可用。图谱存储随默认拓扑启动，但构建需要管理员提交作业，图检索要在查询参数里打开 `use_graph_retrieval`。外部知识连接器（飞书、Dify、Notion）是知识库类型中的可选项，不是默认就会去连接外部系统。

因此，功能上的准确表述是：智能体运行、默认知识检索、多租户权限和沙盒工作区构成不可再瘦的内核；no-knowledge、container/cube、mineru、abridge 以及 OIDC/Langfuse/搜索凭据是少数真实开关或附加集成；其余能力是内核上的显式扩展。下面按域逐项说明每项功能做什么、从哪里进入、是否核心、依赖什么、如何配置和如何定制。

## 2. 智能体定义与预置角色

智能体是可复用的配置，而不是一次对话。它由模型、提示词、工具、知识库、Skills、MCP 和插件选择组成，定义保存在 `agents` 表，以 `slug` 为稳定标识，`backend_id` 指向执行后端。当前注册表只有 `ChatbotAgent`，因此不同产品角色靠 context 区分，而不是靠多套编排框架。定义还包含名称、描述、图标、`config_json`、`share_config`、`visibility`（缺省 `private`）、是否内置、是否默认，以及创建者。用户级环境变量存在 `agent_envs` 中，按 `uid` 唯一，可在设置中编辑并验证，执行时注入，不把密钥写进 Skill 或提示词。

管理入口是网页 `/agent-manage` 与 API `/api/agent`：列出后端、读取默认智能体、按 Skill 创建、读写删除、设为默认，以及维护专属 Skill。公开目录在 `/api/v1/agents`。预置角色由 `modules/agents/presets` 在初始化时同步：`default-chatbot` 名为智能助手，预加载 `chat-widgets`，默认插件包含 `knowledge-base`；`knowledge-base-qa` 名为知识库问答，同样启用该插件，普通 skills 列表为空，强调按需检索；`deep-research` 名为深度研究，绑定 `deep-research` Skill 和专门的系统提示，定位是编排者而不是亲自做完所有检索。发现函数拒绝重复 slug，并保证默认助手在首次入库时排在最前。

共享与私有是功能而不是装饰。普通用户可以创建私有智能体，并在授权范围内选择模型、工具、MCP 和 Skills；管理员可以发布共享定义并配置 `read_scope` 与 `manage_scope`。权限上限是：普通用户对共享智能体最高为读，管理员和超级管理员可以管理。资源选择在运行准备时按当前用户权限解析，模型提示词不能提权。编辑共享定义时，运行中的会话继续使用已冻结的配置快照，新会话才使用新定义。

定制方式包括：新增预设模块并导出 `AgentPreset`；在管理界面创建自己的智能体并选择已有工具与 Skill；若编排方式必须不同，再实现并注册新的 `BaseAgent`。大多数场景不必新增后端。智能体评估没有内置完整产品化套件，官方说明完整评估可通过公开 API 自行构建，见 `docs/agents/agent-evaluation.md`，本树中该文档本身非常短，不应把它写成已经具备与知识库评估同等的内置工作台。

## 3. 会话、队列、回合和运行

会话是独立上下文和输入队列的实例。网页在 `/agent` 与 `/agent/:thread_id` 中工作，外部系统走 `/api/v1/agents/sessions`。用户可以创建会话、搜索、查看、标记已读、归档、查询队列，并读取 items、回执、turns、审计、某个 Run 或 Input。协议把 Session、Thread、Turn、Run、Input 分成可独立寻址的对象，0.8 起旧接口不再兼容。创建和提交支持幂等：Input 有 Receipt，创建 Session 有 `creation_request_id`，重复请求不会生成第二套历史。

一次普通提问的功能步骤是：界面或 API 提交文本、图片、附件、模型与审批配置；服务端锁定线程，校验作用域，保存 Input 原文并把附件绑到 Input，配置在接收时冻结；调度器领取就绪队头，生成正式消息、Turn 和 pending Run；提交后再投给 worker；worker 取得租约、准备 Context、进入 LangGraph；过程事件经 Redis Stream 用 SSE 推送；终态写入 PostgreSQL。前端按 Thread 维护一份 item 状态，历史分页、SSE 和恢复快照写入同一 reducer。断线后先退避重连，过期则读数据库快照，不从相邻 Run 猜测结果。

队列策略是功能的一部分。后续消息按 FIFO 单条领取；纠正性的 steer 优先，并在消费时合并连续就绪前缀。等待用户回答或审批时，普通消息会被拒绝。队列可以暂停，用户提交的恢复消息会占据固定优先位置。未消费的取消不生成消息。这些行为保证多用户、长任务和插话纠正同时存在时，历史仍然可解释。

人工交互有两类等待点。`ask_user_question` 一次提出 1 到 5 个问题，支持纯问答或最多 5 个选项的选择，默认可自行填写，也可允许多选；Web 和 Public API 用 `question_id` 提交回答，CLI 只提示到网页继续。命令执行和 Project 外写入在「请求审批」模式下也会等待；0.8 之后新会话默认「完全信任」，已保存的选择继续有效，也可切回审批。省略审批字段的外部 API 调用保持原契约。等待恢复沿用同一 Turn，产生下一段 Run，而不是新开一轮对话。

协作是内核上的增强，不是独立产品。成员会话拥有独立上下文和自己的队列，共享 Project Workdir，靠父关系和树内路径关联，不继承父历史。系统配置 `max_cooperation_concurrency` 限制一棵树上同时执行的 Run 数，缺省 4。用户可以进入成员会话回答问题、审批或调整方向。普通取消只作用于指定 Turn，显式停止才取消整树。父会话结束不会自动抹掉后代已经开始的工作。同一用户的所有树在 Cube 下共用一个虚拟机。

会话还可以被搜索、置顶、归档，记录最后查看的顶层 Run。用户或智能体可以给 Turn 写反馈，`mark_for_improvement` 会在用户纠正、工具失败或能力缺失时主动留下复盘线索，超级管理员可在系统反馈接口中分页查询。标题由运行时自动生成，失败时回退到可读名称。压缩上下文可以在会话上主动触发。这些都是围绕同一套 Session 事实的功能，而不是另一些模块。

定制时，新的输入通道必须先成为 Input；新的等待类型必须落入已有等待点模型；新的客户端必须使用 Public v1 协议。不要为某个渠道直接写 Message 或绕过租约执行模型。

## 4. 工具系统

工具是智能体产生副作用的唯一正规入口。功能上分成：始终存在的基础工具、按配置或选择进入本轮的通用工具、由沙盒后端提供的文件与命令工具、由插件激活后开放的能力，以及由 MCP（含内置知识 MCP）提供的远程工具。注册在 `modules/extensions/tools`，授权在构图和执行时两次发生。目录接口是 `/api/system/tools/options`。

基础工具集合 `BASE_TOOL_NAMES` 包含 `ask_user_question` 和 `mark_for_improvement`，所有正常 Agent 图都会注册，不受工具勾选或插件状态限制。前者已经在会话章说明。后者要求原因在去掉空白后为 1 到 4000 字，保存为待复盘线索，不表示问题已解决或 Skill 已更新；没有真实 Run 或工具调用 ID 时拒绝保存，同一调用重放返回同一记录。

`present_artifacts` 把当前用户可见的结果文件登记为交付物，前端展示预览、下载和保存到个人空间的卡片。它接受绝对路径列表，只应传入真正要给用户看的文件，而不是中间过程或内部摘要文件。`ocr_parse_file` 把工作区中受支持的 PDF、Office 或图片解析为 Markdown，写到当前 Project Workdir 的 `outputs/ocr/`，返回路径和不超过约 1200 字的预览，完整文本再由 `read_file` 读取。可选参数指定 OCR 引擎，省略时用系统默认。

`web_search` 与 `web_fetch` 只有在管理员于「设置 → 网络搜索」配置了有效供应商和凭据之后，才会进入本轮工具集。搜索支持 Tavily、DeepSeek 和豆包 Custom；抓取支持 Tavily Extract 和 DeepSeek Fetch。豆包只参与搜索，不能把搜索摘要当成任意 URL 的抓取结果。未配置的能力本轮不绑定，执行失败不会自动换一家供应商。测试按钮可以使用未保存的密钥草稿，不改变已保存配置。凭据不进入 Context、Skill 或沙盒环境。目录里出现工具名只证明已注册，不能证明本轮可用。

文件读写和命令执行由沙盒后端提供，经文件系统中间件暴露为 `read_file`、`write_file`、`edit_file`、`glob`、`grep`、`execute`。智能体还应使用 `read_file` 阅读 OCR 或知识库打开后落入工作区的文本。Memory 相关工具 `remember_memory`、`search_thread_messages`、`read_thread_messages` 受用户配置 `enable_memory` 影响。协作工具 `create_session` 用于派生成员会话或独立顶层对话。`load_plugin` 读取插件说明并激活，下一轮才开放其工具。知识工具见知识库章，它们不是本地 `@tool`。

管理端可以在扩展中心查看工具目录。新增内置工具的方法是编写带 `@tool` 的函数并在 builtin 包中显式导入，然后在执行边界再次校验用户和资源。注册不等于对所有智能体授权，也不等于每一轮都会绑定。网络类和数据库类工具尤其不能只靠描述文本约束行为。

## 5. Skills 与部署插件

Skill 提供操作说明，不声明运行依赖，也不保存激活状态。这是功能上必须记住的界限：给智能体一份「如何做调研」或「如何展示图片」的说明书，并不等于安装了一个可执行依赖包。共享 Skill 的目录和版本在 PostgreSQL 中，字节以不可变包形式管理；个人 Skill 的字节在 UserWorkspace 的 `agents/skills`。内置 Skill 目前包括 `chat-widgets`（对话内 Image 与 ImageGroup 等展示组件）、`deep-research`（深度研究方法论）、`image-gen`（在沙盒中生成图片并配合组件展示）和 `mysql-reporter`（带有列出表、描述表和查询的脚本说明）。插件还可以自带 Skill：`knowledge-base` 与 `abridge`。

管理入口是 `/extensions` 下的 Skill 详情，以及 `/api/system/skills` 与 `/api/skills`。普通用户可以查看可访问列表、安装个人 Skill、从远程来源准备安装草稿并确认，也可以读写个人文件；共享 Skill 的内容、文件树、版本、导出、启用和共享范围由具备管理权限的角色维护。内置同步接口可将代码中的内置 Skill 再次同步到共享索引。远程安装有来源限制。正文可以按普通渐进读取，也可在智能体配置里预加载；专属 Skill 绑在某个智能体上，在线编辑不会改写已经开始的运行所准备的正文。

投影是对用户可感知的功能：授权变化后，共享 Skill 会出现或消失在沙盒的只读 Skills 目录中；撤销会先撤下旧投影。个人目录由符号链接指向用户自己的文件。运行中的任务使用准备快照，新任务使用新内容。二次开发新增内置 Skill 应放入 `modules/extensions/skills/builtin` 并走同步通道；不要让运行进程直接改用户配置，也不要绕过修订锁改共享正文。

部署插件比 Skill 更重，而且不能由用户上传代码路径。当前源码只登记 `KnowledgePlugin` 与 `AbridgePlugin`。插件目录提供 `plugin.py` 和可选 `skills/`，必须在 `REGISTERED_PLUGINS` 显式列出。智能体配置里选择插件后，模型调用 `load_plugin`，下一轮才获得其工具或 MCP。知识插件引用内置 `knowledge` MCP；aBridge 插件在加载后由专属中间件注入设备提示并开放设备 MCP，且该 MCP 不能被智能体直接勾选。关闭插件不影响个人设备管理本身。定制新插件必须避免工具重名，入口 Skill 必须包含在声明的 skills 中，并通过既有中间件钩子工作。

## 6. MCP 集成

MCP 让智能体使用远程工具目录。超级管理员在 `/api/system/mcp-servers` 上登记、修改、删除、测试、启用或关闭服务器，并可以开关单个工具。用户可以为需要认证的服务器配置个人 Token、API Key，或完成 OAuth。浏览器授权事务绑定用户、浏览器和配置修订，回调必须由当前登录用户确认。连接行锁串行化刷新与断开，世代号阻止旧回调恢复授权。每次出站都会复查当前用户、配置、工具和连接。未连接时普通聊天仍可用；仅靠该插件开放的能力在未连接时关闭，但智能体上独立选择的其它合法能力保留。工具目录按本次 Run 发现一次并在运行内复用，新 Run 重新发现。

内置清单有三项。`knowledge` 指向本进程 `http://api:5050/api/mcp`，委托认证，缺省启用，关闭知识部署时能力不可用但身份保留。`abridge` 指向 `http://abridge:8765/mcp`，同样委托认证、缺省启用，但必须经插件加载。`deepwiki-official` 指向公开的 DeepWiki MCP，用于查询公开 GitHub 仓库文档，不按委托模式默认启用。通用 MCP 装配不解释知识库的范围或结果结构；知识引用转换由 Knowledge 自己的模块拥有。

OAuth 过期尝试由 worker 每分钟清理。个人凭证字段属于 business Schema 演进的一部分，已有部署要按文档做显式升级，运行进程不会自动改表。二次开发适配新的个人 OAuth MCP，应遵循 `docs/agents/mcp-integration.md` 中的协议与适配边界，把配置、协议、授权事务和 HTTP 适配放在已有模块，而不是在智能体提示词里硬编码令牌。

## 7. 沙盒、工作区与文件交付

沙盒和工作区把对话结果变成可继续使用的文件，这是内核功能。每个 Project 绑定一个相对 UserWorkspace 的 `workdir_path`。managed 目录由服务端按日期和短标识创建；linked 目录绑定用户工作区里通过 no-follow 校验的已有文件夹。项目可以是隐式或可选，隐式项目允许没有名称。多个项目可以共享同一路径，但会话上的项目绑定不可变。网页 `/workspace` 提供树、搜索、上传、下载、读写和建目录；预览器走 `/api/viewer/filesystem`；知识库文件可以通过 `/api/workspace/knowledge/*` 只读映射进工作区视图。删除项目前不能有活跃回合或待处理输入。

智能体在沙盒中看到的路径是虚拟绝对路径：工作区根 `/home/user/workspace`，共享 Skill `/home/user/skills`，个人 Skill `/home/user/workspace/agents/skills`。用户在界面里看到的是 scope 相对路径。两种表示由 workspace 模块转换，宿主真实路径不离开该模块。交付物、预览、附件准备和协作成员都使用同一持久目录。内部目录 `large_tool_results`、`conversation_history`、`tool_media` 不作为交付卡片展示。

执行后端必须在 Container 与 Cube 中选择。Container 是默认和官方快速开始路径：每个 Run 使用临时容器，工作目录文件持久保留，默认无网络，资源有内存、CPU、PID、家目录、临时目录、容器数、并发 exec 和生命周期上限。用户可在 `/api/user/sandbox` 请求重建或查看磁盘用量。Cube 提供持久用户虚拟机和更强隔离，空闲五分钟休眠，文件访问可唤醒，重建保留工作区与 Skills。审批模式决定命令和跨项目写入是否先问人；默认完全信任并不允许写出授权目录。二次开发应通过已有文件工具和 `present_artifacts` 交付结果，而不是自己调用容器引擎。

附件与图片是会话功能的一部分。附件在接收时绑定 Input，经统一准备进入当前 Project Workdir。聊天图片走多模态直读，单条最多 10 张、base64 总量 80 MiB，前端在发请求前做同值校验，后端是权威；其它文件仍走附件通道。`chat-widgets` 可以直接在对话里展示图片，不必先登记交付物。解析附件可调用 `ocr_parse_file`。预览支持 Markdown、PDF、HTML、文本与代码、图片；`.docx` 与 `.pptx` 可通过 LibreOffice 转为 PDF 预览，缺省超时 60 秒；读取预算上限为 30 MiB，文本预览最多 25 万字符。这些限制都是功能契约，定制预览时必须继续遵守，而不能把整个对象一次性读进内存。

## 8. 知识库与检索

在默认部署里，知识库是核心功能。管理员在扩展中心创建库，类型由工厂登记：本地可写的 Milvus，以及只读的飞书、Dify、Notion 连接器。库有名称、描述、嵌入模型、可选 LLM、查询参数、分块等附加参数、共享范围和示例问题。未删除库的名称小写后全局唯一。共享范围与智能体相同，使用读范围和管理范围；普通用户对共享库最高为读，管理员可以管理。入口是 `/extensions/knowledge-bases/:kbId` 与 `/api/knowledge`。

Milvus 库支持上传、从白名单 URL 导入、从工作区导入、维护目录树、解析、索引、重解析、编辑 Markdown、检索测试、导出和统计。支持的文件类型包括常见文本、Office、PDF、图片，以及必须包含 UTF-8 Markdown 的 ZIP。目录和文件共用一张表，同一父目录下未删除名称唯一，文件名必须是干净叶子名。状态从 uploaded 经 parsing、parsed、indexing 到达 indexed，错误态可重试；目录创建即为 `done`。软删除先改 PostgreSQL，再经投影 outbox 清理向量投影。导入有幂等回执，删除后不能用同一请求复活。文件带有代次，重建时不会把尚未投影成功的新版本当成当前对外版本。

分块预设包括 `general`（默认）、`qa`、`book`、`laws`、`semantic`、`separator`，引擎版本为 `ragflow_like_v1`。库、文件和单次请求三层参数合并。检索模式可选向量、BM25 或混合，缺省向量；可设必含词、排除词、完整短语、高亮、最终返回数（缺省 10，上限 100）、相似度阈值、BM25 候选数和融合权重。图检索另见下一章。评估功能允许上传或自动生成问答集（含单跳与多跳），批量跑检索指标，在有参考答案和评判模型时评估答案质量；作业只对管理员开放。示例问题可以生成和保存，便于在界面里做回归检查。

智能体使用知识库的方式是按需调用五个只读工具：列出可见库、按库检索片段、在文件中查找、按文件分段打开原文、按文件名搜索。工具来自内置知识 MCP，需启用 `knowledge-base` 插件并 `load_plugin` 后在下一轮开放。每次调用都按当前用户权限和会话选择复核，引用保留文件身份和行范围。外部系统可通过 `/api/v1/knowledge/tools/*` 或 `/api/mcp` 使用同一组工具，认证为 API Key；内部 Agent 使用短期委托。关闭知识后这些入口不再可用。

只读连接器按各自凭据查询外部内容，不在 Yuxi 中保存源文档副本，支持的操作以连接器为准。它们适合「已经把资料放在飞书或 Notion、只希望智能体能够检索」的场景，不能代替本地入库和图谱构建。二次开发若要增加一种外部源，应实现执行器并注册类型，明确声明是否支持本地文档。

## 9. 知识图谱

图谱在功能上是知识库的增强索引，不是第二条必须跑起来的问答产品。默认拓扑会启动 Neo4j，并从已索引的 Milvus 文档块抽取实体和关系。构建不会在解析完成后自动开始，管理员要在库详情中配置抽取模型并提交作业。抽取器当前只有 `llm` 一种，依赖聊天模型输出严格 JSON，缺省超时 60 秒，最大 600 秒，实体名、标签和关系类型有长度上限。作业分两阶段：结构写入后标记 `graph_structure_indexed`，向量回填完成后才标记 `graph_indexed`。管理接口提供整库或按文件的状态、失败块查看、单文件清理、重置和对账。浏览接口提供列表、子图、标签和统计，可按关键词搜索实体并查看节点详情。

检索时，图检索缺省关闭。打开 `use_graph_retrieval` 后，才按实体召回数、三元组召回数、最大节点数（缺省 10000，硬上限 50000）、路径召回块数和融合权重，与文本检索做排名融合。因此「默认有图谱存储」和「每次回答都走图谱」不是同一件事。关闭整个知识能力时，Neo4j 进程也会被叠加文件缩到 0。二次开发若要增加非 LLM 抽取器，需要在抽取器工厂登记；若只是不想用图，可以不提交构建、不打开图检索，而不必先拆掉默认拓扑——除非决定整段关闭知识。

## 10. 文档解析与 OCR

解析把原件变成带相对图片引用的 Markdown 目录，供知识入库或会话附件使用。引擎按需加载，不在 API 启动时全部初始化。系统默认引擎可在「设置 → OCR 配置」中选择，单次解析或工具调用可以覆盖。RapidOCR 是随 API 安装的本地默认轻量方案，第一次实际解析时加载 ONNX 模型，模型目录优先 `RAPIDOCR_MODEL_DIR`。自托管 MinerU 需要 `--profile all` 或外接符合 4.1 Tasks 协议的实例，默认地址 `http://mineru-api:30001`。官方云 MinerU 使用另一套 v4 接口，可选择 Pipeline 或 VLM 模型，不能只靠改 URL 与自托管互通。DeepSeek OCR 与三套 PaddleOCR 云服务走相应适配器，需要配置令牌和地址。健康检查接口 `/api/system/ocr/health` 与选项目录 `/api/system/ocr/options` 给管理页提供可用性信息。凭据在数据库中脱敏保存，空值回退环境变量，接口不回显环境中的密钥。

HTML 默认复制本地引用图片，缺失或越界会使整篇失败，也可用 `html_text_only` 只保留 alt 文本。URL 导入受白名单约束，未配置时默认关闭。PDF 禁用 OCR 时只读文本层，扫描件通常得不到内容，图片必须启用 OCR。这些都是功能限制，不是隐患清单。定制新引擎要在 `ENGINE_SPECS` 登记标识、显示名、扩展名和实现类，并保持惰性加载。

## 11. 模型与供应商

没有可用的聊天模型，智能体无法运行；没有嵌入模型，Milvus 知识库无法索引。模型因此属于内核依赖，但具体供应商是可替换配置。初始化脚本无条件要求填写 `SILICONFLOW_API_KEY`，即使生产打算使用其它供应商。这只保证引导过程能写入一个缺省来源，登录后仍可在「智能体 → 模型供应商」管理全部来源。内置清单包括 OpenAI、DeepSeek、多组 DashScope 与阿里云 Coding Plan、智谱与 Z.AI、小米 MiMo、Kimi Code、Moonshot、MiniMax、OpenRouter、ModelScope、OpenCode，以及硅基流动国内站和国际站。国内站预置了聊天、嵌入和重排的启用模型，并声明三类能力。Anthropic 与 Google Gemini 在源码中被注释，不能当成已交付内置项。用量元数据被标记为不可信的供应商包括 `siliconflow-cn` 和 `siliconflow`，其累计不会进入 Run 与 Thread 聚合。

管理员可以添加自定义 OpenAI 兼容端点（例如 Ollama），从远程列表挑选或手动添加模型，配置请求参数，刷新缓存，查看状态。系统配置指定默认聊天模型、快速模型、引用模型、嵌入和重排。按用户统计用量需要额外的请求头与网关验签，见 `docs/advanced/model-usage-tracking.md`，不是开箱即有的账单系统。更换或移除模型不会改写已经冻结在会话里的配置快照。二次开发若要增加内置供应商，应改 `BUILTIN_PROVIDERS` 并诚实声明能力与用量是否可信；大多数情况下用管理界面添加兼容端点即可。

## 12. 租户、身份与管理

多用户和权限是内核。角色分为超级管理员、管理员和普通用户。首次运行必须初始化超级管理员。此后可管理部门、创建和停用用户、重置资料和密码、上传头像。账号连续失败 5 次锁定 300 秒，同时按 IP 与账号、按 IP 全局在 10 分钟窗口内限速，生产必须由反向代理提供真实客户端地址。软删除不会让账号继续登录。用户可修改个人资料、密码、记忆开关和 Agent 环境变量。

API Key 可在用户页创建，级别只能是 `full`、`agents` 或 `knowledge`，可绑定应用 ID、过期时间和部门。原始密钥只在创建时出现，之后只存哈希。撤销不可复活，同一创建请求可以恢复响应。Public API 用 Key 识别调用者，并把应用与终端用户的会话隔开。CLI 使用设备码：终端发起会话，用户在网页 `/auth/cli/authorize` 批准后，终端换取密钥。

企业 OIDC 默认关闭，打开后由部署方已有的认证中心提供登录，本地仍检查锁定、删除和人类用户类型。Yuxi 自己也可以作为限定静态客户端的 OIDC 签发端，供 aBridge 一类集成使用，必须配置独立 RSA 密钥，不保存第三方认证数据库模板。Dashboard 仅超级管理员可访问，提供用户、虚拟机、工具、智能体、调用时序和会话审计。系统配置、品牌信息、OCR、网络搜索、资源所有权变更都在系统域下。品牌定制通过本地配置和重新加载完成，不在本文展开操作步骤。

这些管理功能使「私有部署的多用户工作区」成立。它们不是可以卸掉的企业选配；没有它们，共享知识库和共享智能体就没有授权对象。二次开发接入已有账号应走 OIDC，接入业务系统应走分级 API Key，而不是复用超管会话。

## 13. 外部集成：CLI、公开 API、观测与设备桥

命令行包 `@xerrors/yuxi` 版本 `0.1.0`，与平台包版本不同。它能登录、对话、发附件和图片、查看 Thread、在知识开启时查询知识库。它不能做评估实验、知识库管理、MCP/Skill/模型与系统配置，也不能在终端完成审批或回答等待点。仓库源码不代表 npm 已发布，旧 Python CLI 配置不会导入。discovery 中的 `min_cli_version` 与该包版本一致，知识相关子能力随开关变化。

公开 Agent API 是网页和外部系统共用的会话协议，文档见 `docs/advanced/agents-public-api.md` 与入门页。它覆盖创建与提交、图片与文件、错误与重试、断线恢复、等待、取消与队列、读取与事件。知识工具 API 是另一组稳定入口。二者都要求正确级别的 API Key。完整智能体评估需要调用方自行用这些 API 构建。

Langfuse 是可选观测：配置后可以看到 Turn 级追踪和 Run 级观察，但不能代替数据库终态，也不应作为恢复依据。aBridge 是可选设备桥：需要叠加编排和初始化脚本，智能体通过插件使用已授权的电脑和浏览器设备，每次出站签发最长一分钟的委托，不保存个人 refresh token。这些集成丰富了场景，但关掉它们不会拆掉内核。

## 14. 定时任务、后台作业和运行治理

用户可以创建定时 Agent：指定项目、智能体、提示词、cron 表达式、时区、可选模型和审批模式（只允许默认或始终信任）。到点后系统复用同一套会话运行模型，而不是在 cron 里直接调模型。接口在 `/api/scheduled-tasks`，可立即运行、修改、查看运行记录或删除。创建支持幂等。这是内核运行链路上的调度功能，依赖项目与智能体已经存在。

后台作业承担知识解析、评估和图谱构建。管理员可在 `/api/background-jobs` 查看、取消或删除。作业有租约、心跳和取消检查点，全局同时处于 running 的领取上限为 4，避免挤占对话执行槽。投影清理在知识开启时由 worker 定时推进。用户在界面上看到的解析进度、评估分数和建图状态，都来自这些作业的观察记录，而不是 API 请求同步跑完整个入库。

并发容量是运行治理的一部分。规划文档按单 worker、约 100 个同时运行的 AgentRun 建议 `ARQ_MAX_JOBS=140`；代码在环境变量缺失时的缺省是 10，部署必须显式配置，不能假定建议值已经生效。单任务业务时限缺省 3600 秒，由 `YUXI_JOB_TIMEOUT_SECONDS` 调整。协作树另有自己的并发上限。这些数字影响功能是否在负载下仍可交互，但它们不是另一些产品特性。

## 15. 限制、版本与明确不在范围内的事项

0.8 只面向全新部署，不提供从 0.7.x 原地升级的程序。API 与 worker 在 Schema 域版本不匹配时拒绝启动。知识域 v1 到 v2 的目录转换是离线入口。本树 business 版本已经是 4，与发行说明里曾经出现的 business 2 表述不同，必须以源码常量为准。官方教程使用 `v0.8.0` 标签；本分析树是更新的 `main`。应用镜像需本机构建，没有现成的一键拉取应用镜像作为官方唯一路径。生产 Web 只提供 HTTP 80，TLS 要由部署方加在前面。Container 共享内核，临时软件和登录态不跨执行段保留，默认无网络。CLI 不覆盖管理面和等待点。智能体完整评估不内置工作台。对话内旧 HTML Preview、知识库思维导图、旧 SubAgent 专用入口和待办清单工具等已退出。Anthropic 与 Gemini 内置项被注释，未交付。硅基流动用量不可直接当作账单。discovery 关闭知识并不删除数据。同一数据目录不允许两套环境同时写入。`make reset` 只删除默认 `docker/volumes`，外部 `YUXI_STATE_DIR` 会被拒绝删除。

源码或官方文档没有写成产品功能的事情，本文不扩展为承诺。例如仓库没有 Helm 安装路径，没有把 Yuxi 描述为多集群自动运维平台，也没有把每一种模型供应商的计费精度写成平台保证。超出本树实现的能力，应视为二次开发自己要建造的部分，而不是遗漏未写的官方功能。

## 16. 面向二次开发的定制场景

把上面的功能收成几条可执行的定制路径，有助于避免「先关掉一堆模块才能开始」。

若目标是企业内部资料问答：保留默认拓扑和知识开关，配置聊天、嵌入和可选重排，创建 Milvus 知识库，按部门设置共享范围，用 `knowledge-base-qa` 或自行配置的智能体启用知识插件，用检索测试和评估集检查召回。需要关系推理时再提交图谱构建并打开图检索。不需要自托管 MinerU 就先用 RapidOCR 或云端 OCR。

若目标是让智能体在受控目录里完成多步骤办公或研发辅助：用默认助手或自建智能体，编写 Skill 描述流程，必要时增加内置工具或接入 MCP，用 Container 或 Cube 执行命令，用 `present_artifacts` 交付文件，用审批模式决定是否要人确认。知识库按需引用，而不是先建设完整图谱。

若目标是深度调研：直接使用 `deep-research` 预置和对应 Skill，配置网络搜索，允许协作会话并行核验，并在最终报告中保留引用。这仍然跑在同一个 `ChatbotAgent` 上。

若目标是把智能体嵌进已有业务系统：发放 `agents` 或 `full` 级别 API Key，按 Public v1 创建会话、提交消息、读取事件和结果；需要检索资料时再发放 knowledge 级别或使用知识 MCP。不要去调用前端内部接口。等待点和审批要在自己的界面或回退到 Yuxi 网页处理。

若当前阶段完全不需要知识：用 no-knowledge 叠加关闭运行能力，仍然保留会话、权限和沙盒。这是明确支持的瘦身，而且是少数几种被允许的瘦身之一。它不会把产品变成「可以继续无限删模块」的框架，只是去掉默认打开的知识运行面。

若需要企业统一登录或个人电脑设备：再打开 OIDC 或 aBridge。它们不改变核心对象模型，只替换登录方式或增加一类经插件加载的工具。

无论哪条路径，定制都应落在预设、工具、Skill、插件、供应商、解析器、知识类型和薄路由这些登记点上。把队列改成同步阻塞、把知识检索写回提示词硬拼接、把宿主路径交给模型、把 Container 默认联网去模拟开发机，都会损害这个功能内核的可维护性。Yuxi 适合二次开发，正是因为功能已经收成一条可以理解的主链，并且用少数开关诚实标出哪些部分可以暂时不要。沿着这条主链为自己的场景加说明、加工具、加模型，而不是先做一次企业级裁剪，才是本树所支持的使用方式。


## 17. 工作台里的提及、引用、过程展示和导航

统一工作台除了发送消息，还提供一组围绕「当前这一轮正在做什么」的功能。用户可以用 `@` 引入知识库、文件或特定 Skill，也可以引用插件和其它会话。提及接口在 `/api/mention`：`GET /plugins` 返回当前 Web 会话已启用且用户可读的插件，仅接受网页登录，不接受 API Key 调用；`GET /sessions` 按标题和活动时间检索可引用的对话；`GET /search` 在授权范围内搜索可提及的资源。把提及写成消息中的结构化引用后，运行准备会按当前权限解析这些选择，模型提示词不能单独扩大范围。插件提及的语义是明确要求使用该插件，智能体应先 `load_plugin` 再按其说明行动。

回答来源标注是知识功能在工作台中的出口。Turn 可以保存引用，接口在 `/api/agent/threads/{thread_id}/turns/{turn_id}/references`。引用来自知识工具结果中的文件身份和行范围，用户可以从命中片段回到原文核对。这要求知识工具真正被调用过，而不是只在提示词里「参考了某库」。过程展示则把任务拆解、工具调用状态、上下文 Token 消耗和执行树呈现出来，长任务不再是黑盒等待。前端按工具结果投影区分搜索失败、成功但空列表、以及历史里带错误字段的完成态。协作成员的状态、审批卡片和交付卡片也在同一时间线中出现。会话导航和输入来源查询在 `/api/agent/threads/{thread_id}/navigation` 与 `input-origins`，用于在协作树或关联输入之间跳转。Langfuse 链接在对应 Turn 或反馈记录上可查，但是否能打开外部追踪取决于有没有配置观测。

这些界面功能都属于内核工作台，而不是可关闭的仪表盘插件。关掉知识后，提及知识库和来源标注会缺少对象，但会话、工具过程和文件交付仍然在。二次开发若要改工作台，应扩展既有投影和提及服务，并继续把 API Key 调用挡在仅供网页使用的提及接口之外。

## 18. 知识库管理动作的完整路径

创建知识库之后，管理员实际会用到的动作比「上传再提问」更多，这些动作都在 `/api/knowledge` 下，对应扩展中心里的库详情页。

库级动作包括：列出全部或当前可访问库，创建、读取、更新、删除，生成描述，查看统计，读取支持的库类型和分块预设，导出整个库。删除是软删除加异步投影清理，不是立刻抹掉所有远端索引。查询参数可以读取和更新，查询测试不会把临时参数写回库配置。示例问题可以生成和查看，作为固定检查集。

文档动作分为登记、解析和索引三步，也可以组合。上传接口先把原件放到对象存储并登记文件；也可以从白名单 URL 抓取，或从工作区导入已有文件。解析可以针对单个文件、批量待解析文件，或在登记后单独触发；索引同理。文件详情提供基本信息、解析后的 Markdown 和正文，Markdown 可以写回后再索引。支持按目录新建文件夹、重命名、移动文件，以及按名称搜索和检查重名。批量删除与单文件删除都会进入状态机和 outbox。图片对象通过库内图片路径读取，供解析产物里的相对引用使用。支持类型查询给前端上传框提供允许的扩展名。

对只读连接器，创建库时填写外部凭据和连接参数，之后主要使用查询，而不是本地解析索引。飞书、Dify、Notion 的具体字段以各执行器和管理文档为准，本文不编造未在分析中展开的请求体。连接失败应表现为明确错误，而不是空检索成功。

图谱构建动作独立于解析：配置抽取、提交索引、查看库级或文件级状态、查看失败块、清理单文件图谱、重置和对账。浏览动作在 `/api/graph`。评估动作在 `/api/evaluation`：上传 JSONL 数据集、列出和下载、删除、自动生成（可恢复）、创建评估运行、查看运行和指标、删除运行。生成和评估都是后台作业，界面应显示作业进度而不是让浏览器同步等待。

智能体侧不重复这些管理动作。Agent 只调用五个只读工具。CLI 在知识开启时可以列出库、列文件、查询、打开和查找，但不能上传和管理。这个分工是功能设计：管理是管理员的工作台，检索是运行时能力，命令行只覆盖后者中已稳定的部分。

二次开发若要做自动入库流水线，应调用文档导入与查询 API，并遵守幂等回执和状态机，而不是直接写 Milvus 或 MinIO。若只要让业务系统提问，应调用知识工具 API 或 MCP，并使用 knowledge 或 full 级别的密钥。

## 19. 评估功能怎么用，以及它不是什么

知识库评估测试的是检索质量和可选的答案质量，不是智能体整个工具循环的打分。管理员准备基准问答集，每条包含查询、可选的金标块和参考答案。可以从 JSONL 上传，也可以让系统根据库内容自动生成单条或多跳问题，生成作业可以恢复。运行评估时指定检索配置，系统按条检索，计算召回类指标；若提供参考答案和评判模型，再生成答案并评估准确性。结果按运行和条目保存，可比较不同配置。限制写在介绍文档中，例如评估依赖已索引内容、生成质量和评判模型都会影响结果解释，不能把一次分数当成唯一上线标准。

智能体评估是另一回事。官方明确完整智能体评估要通过公开 API 自行构建，本树没有与知识评估对等的内置「智能体基准工作台」。二次开发若需要回归智能体行为，应使用 Public v1 创建会话、提交固定提示、读取结果，并在自己的系统里比对；也可以结合 Langfuse，但那是可选观测，不是内置评分器。不要把知识评估分数直接解释成智能体任务成功率。

## 20. 模型、搜索和系统选项的日常配置

日常配置分成「改完要重建容器的部署项」和「管理员在界面保存后即可按规则生效的系统项」。前者包括知识开关、沙盒后端、数据库地址、CORS、OIDC 开关等。后者包括默认模型、快速模型、引用模型、嵌入和重排、协作深度与并发、默认 OCR 引擎、网络搜索与抓取供应商。优先级是代码默认值小于环境变量，再小于数据库中保存的非空值；列表字段会保留明确保存的空列表，不会偷偷回退。OCR 和搜索的密钥留空表示保留原值，勾选清除后才回到环境变量。

模型供应商页支持列出内置与自定义来源、添加和编辑、删除、拉取远程模型、刷新缓存和查看状态。为知识库选择嵌入模型、为图谱抽取选择聊天模型、为智能体选择对话模型，都在已启用的规格里完成。用户级 Agent 环境变量有单独的读取、保存和校验接口，适合放个人令牌类值，但仍由服务端持有，不进入沙盒用户环境，除非实现明确注入且经过用户保存。网络搜索页除了保存供应商和密钥，还可以分别测试搜索和抓取；豆包只测搜索。测试可能消耗供应商额度，空结果不算通过。

系统 discovery 和就绪探针是配置是否生效的第一观察点。只改环境文件却不重建 API 或 worker，界面里的有效值可能仍是旧的。知识开关尤其如此。二次开发增加可运行时修改的选项，应在所属模块声明 Option，交给 system 模块做持久化、脱敏和缓存，而不是在自己的路由里另存一份配置文件。

## 21. 用户、部门、密钥和审计的操作边界

超级管理员可以管理所有用户和部门，可以访问 Dashboard 和集中反馈。管理员可以管理部门内的普通用户，但不能把别人提升为管理员或操作超级管理员。普通用户管理自己的资料、密钥、环境变量、个人 Skill 和 MCP 个人连接，并使用被共享给自己的智能体与知识库。部门接口支持列表、创建、读取、更新和删除。用户接口支持分页、按角色筛选、校验用户名和 uid、上传头像、修改密码。锁定与限速在登录功能中自动发生，管理员需要理解「用户被锁」和「来源 IP 被限速」是两层。

API Key 的操作包括列出、按应用分组查看、创建、读取、修改和删除（撤销）。级别必须在三种之中选择。Public API 对智能体协议接受 `full` 或 `agents`，对知识工具接受相应级别。把一把 `full` 密钥发给只需要检索的下游系统，是功能误用而不是架构缺陷。CLI 登录是密钥创建的一种受控方式，批准页必须是已登录的人类用户。

Dashboard 提供实例级观察：总览统计、按用户、按虚拟机、按工具、按智能体、调用时序、会话列表和会话详情。它服务于治理，不是普通用户的工作台。反馈查询支持按智能体、来源（用户或智能体）、评分（喜欢或不喜欢）分页过滤，仅超级管理员。模型用量统计若要按用户汇总到外部网关，需要按用量文档配置签名，否则只能依赖本系统记录的、且被判定为可信的 usage。

二次开发若要对接人力资源系统，较稳妥的是用 OIDC 进入已有用户，再用部门与共享范围表达组织，而不是在 Yuxi 外再维护一套平行账号并共用密码。若要对接审计平台，应从 Dashboard 和反馈、以及可选的 Langfuse 导出观察，不要读取 Redis 事件流当做法务日志。

## 22. 设备、品牌和其它附加功能

设备列表在 `/api/devices`，服务于 aBridge 一类「把个人电脑或浏览器授权给智能体使用」的场景。没有叠加 aBridge 编排并完成初始化时，不应把该功能当成已经可用的核心能力。启用后，用户管理个人设备授权，智能体通过插件加载获得工具；关闭插件并不删除个人设备管理本身。委托令牌短时有效，不保存个人 refresh token。

品牌定制允许修改站点信息和主题，配置后重新加载，登录协议页也会使用新的品牌字段。这是部署级的产品化功能，不改变对象模型。它适合把私有部署做成自己的门户外观，但不提供多品牌、多站点的完整 CMS。

会话压缩、Memory 开关、消息活动查询、沙盒重建和磁盘用量，都是用户或管理员可以直接触发的维护功能。压缩减少上下文体积，失败和恢复规则见机制文档，功能上应视为可能改变后续回答所依赖的历史视图，而不是无损折叠。Memory 关闭后，记忆工具不再按启用路径工作。沙盒重建会保留工作区与 Skills 的持久文件，但 Container 中的临时执行环境不会跨 Run 保留软件安装状态。这些细节决定了「让智能体自己 apt install」不能成为跨会话的可靠功能，除非改用 Cube 的持久环境，并且仍然要满足安全和审批约束。

## 23. 把开关映射到功能菜单

为了让二次开发者在裁剪时不误删内核，下面用功能菜单的语言对照开关。

始终应该保留的功能菜单：登录与首次初始化、用户与部门、API Key、智能体定义与预置角色、会话工作台、输入队列与等待点、基础工具、沙盒文件与命令、工作区与预览、交付物、定时任务（若业务需要到点执行，它仍走同一内核）、系统就绪与 discovery、公开 Agent API。

默认打开、但可以用 no-knowledge 整段拿掉运行面的功能菜单：知识库管理、入库解析索引、检索测试、评估、知识工具与知识 MCP、图谱构建与浏览、工作区中的知识只读视图、discovery 中的知识能力位、知识相关 CLI 子能力。数据可以保留。

必须二选一、不能「什么后端都不配还宣称能执行命令」的功能：Container 沙盒或 Cube 沙盒。选 Container 就要有 runner 与镜像；选 Cube 就要有 KVM 节点和共享目录。

可选增加的功能菜单：自托管 MinerU、云端或其它 OCR 引擎、网络搜索与抓取、外部知识连接器、企业 OIDC、Yuxi 作为签发端、aBridge 设备、Langfuse、用量网关统计、品牌定制、DeepWiki 等非默认启用的内置 MCP。不加这些，内核问答和文件任务仍可在配置了模型之后进行。

明确不要当成还存在的功能：旧 Python CLI 自动迁移、0.7 原地升级、Helm 安装、对话内已移除的 HTML Preview 和知识思维导图入口、被注释的 Anthropic/Gemini 内置供应商、把硅基流动 usage 当账单、CLI 内完成审批、内置完整智能体评测台。

## 24. 场景定制时的功能检查清单

在自己的场景落地时，可以用下面的检查清单核对功能是否真的闭合，而不是只看到容器已经起来。

模型是否已在供应商页启用，并且系统默认聊天模型可用？若要入库，嵌入模型是否可用？若要重排或评估生成，相应模型是否已选？知识若需要，库是否已共享给目标用户，文档是否达到 indexed，检索测试是否能命中？智能体是否选择了正确的插件和 Skill，当前用户是否对它们有读权限？沙盒后端是否与 Compose profile 一致，runner 或 Cube 健康是否通过，工作区里能否看到智能体写下的文件？审批模式是否符合该场景的风险？若用外部系统调用，密钥级别、幂等和事件恢复是否按 Public v1 实现？若关闭知识，客户端是否重新做了 discovery，不要继续调用知识工具？若使用搜索，本轮对话里工具是否真正绑定（而不仅是目录里有名字）？定时任务是否绑在正确的项目和时区？生产是否显式设置了 `ARQ_MAX_JOBS` 等容量参数，而不是停留在代码缺省 10？

这份清单里的每一项都能在源码或官方文档中找到对应接口或配置项。它刻意不包含「先关闭十个企业模块」。Yuxi 的功能文档落到实践上，就是沿着这条清单把内核跑通，再只打开自己的场景所需要的那些可选开关。

## 25. 功能层面的结论

Yuxi 在本树中展现的功能形状，与架构上的紧凑核心是一致的。用户能看到的工作台、知识库、图谱、扩展中心和管理面，几乎都挂在同一条「配置智能体、执行会话、引用知识、交付文件、按组织授权」的链路上。真正能拿掉的运行面主要是知识相关服务，真正能替换的是沙盒隔离模型和解析引擎，真正能后装的是登录、设备、观测和搜索。剩下的能力看起来很多，但它们是这条链路的不同出口：提及和引用是工作台出口，评估是知识质量出口，公开 API 和 CLI 是集成出口，Dashboard 是治理出口。二次开发应当在这些出口上接自己的场景，而不是把出口误认成可以任意拆卸的独立产品。承认少数开关的存在，同时坚持内核不能再随意变瘦，才是对这套功能集最准确的用法。


## 26. 协作工具的完整能力

前文把协作概括为「派生会话并共享工作目录」，运行时实际向模型开放的工具比单个 `create_session` 更多，它们都由 `CooperationMiddleware` 注册，属于内核运行时能力，而不是单独的可选插件。

`create_session` 创建会话并提交初始工作。默认 `mode=child` 创建直属子会话，`mode=root` 创建继承当前项目的独立顶层对话。名称只填局部单段。可以指定 `list_agents` 返回的 `agent_id` 以使用目标智能体的配置和模型；省略时继承派发方的配置与实际模型。项目、工作目录和审批模式沿用派发方。返回的会话标识和初始 `input_id` 是后续等待与取结果的依据。成员不继承父对话历史，派发描述必须自包含目标和必要证据。

`submit_input` 向当前用户与同一 APP 作用域下的已有 Session 提交新工作，目标忙碌时排队，正在等待用户时拒绝。`send_message` 只投递信息，不创建 Turn，也不唤醒空闲会话，适合告知而不派工。`cancel_turn` 取消目标 Session 中精确的一轮，保留历史和已经产生的副作用。`list_sessions` 默认查看当前项目全部会话，显式 `scope=all` 才看更广的历史，每页最多 10 条，支持 offset，返回精简进度而不包含结果正文。`list_agents` 列出当前执行用户可调用的智能体，只返回 id、名称和描述。`get_result` 按 `input_id` 或 `turn_id` 二选一读取精确结果，并且声明下一轮不会覆盖这份结果。`wait_inputs` 等待 1 到 100 个已提交的 `input_id` 全部结束，返回各任务精确结果，等待期间释放执行名额，避免把协作树的并发上限占死。`wait_sessions` 等待指定会话更新，必须使用上次返回的游标，避免重复消费。

深度研究预置正是这些工具的一个场景化用法：先澄清范围，再把正交的子问题并行派发给调研探索员，对关键论断再派事实核查员，最后由编排者综合成带引用的报告；整棵树同时执行的会话数仍受系统配置限制，技能说明里写的「最多四个」与缺省 `max_cooperation_concurrency` 一致，但真正生效的是当前系统配置值。二次开发若要做自己的多角色流程，应编写 Skill 来约定如何调用这组已有工具，而不是再实现一套会话派生 API。若要限制某类智能体不能开子会话，应在授权和中间件装配上处理，而不能只靠提示词。

## 27. 内置 Skill 作为场景模板

内置 Skill 展示了「核心能力已经足够、场景靠说明书定制」这一判断在功能上的含义。它们不增加新的系统进程，只告诉智能体如何组合已有工具。

`chat-widgets` 默认被智能助手预加载。它说明何时在最终回复中用 Markdown 围栏输出 `widget` 协议，以直接展示图片、图文卡片、柱状或折线图表，或用表单收集条件。单张图用 Image，多张用 ImageGroup，短语放在 caption；需要比较或说明时用 Card、Row、Col 组合；分类比较用柱状图，时间趋势用折线图；多条件收集用 Form、文本、单选和日期。组件不必创建文件或执行脚本。围栏必须出现在最后一次工具调用之后的最终回复中，普通文字回答仍用 Markdown。前端负责渲染，后端不把这套协议当成另一种消息表。二次开发可以增加自己的展示约定，但要确认前端渲染器是否认识新的组件类型，不能只改 Skill 正文就假设新组件会显示。

`image-gen` 说明如何在沙盒中调用文生图接口并保存图片。默认示例指向硅基流动的 Qwen-Image 接口，并写明必须在沙盒执行环境中读取 `SILICONFLOW_API_KEY`，不要依赖后端进程的环境变量。流程是：整理提示词，在沙盒脚本里请求生成、下载或解码图片，保存到当前 Workdir 的合适位置，再按 `chat-widgets` 用虚拟绝对路径展示，需要下载时同时调用 `present_artifacts`。最终回复不应把外部临时 URL 当作结果。这表明「图片生成」在本树中是 Skill 加沙盒加环境变量的组合，而不是单独的平台图片服务。要换成其它兼容接口，应改 Skill 或用户环境变量，而不是先找一个不存在的「绘图模块开关」。

`mysql-reporter` 说明如何用技能自带脚本查询 MySQL 并生成报表。智能体应进入 `/home/user/skills/mysql-reporter`，用 `list_tables.py`、`describe_table.py` 和 `query.py` 完成只读查询，再用 Markdown 表格说明结论。脚本只读取沙盒环境变量 `MYSQL_HOST`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE`，可选端口和数据库说明；不读取后端 `.env` 或 Compose 变量。缺少配置时必须明确请用户在个人设置的「沙盒环境变量」中填写，保存后只对新建沙盒或新会话生效，不能猜测连接信息。技能还要求不要调用所谓平台内置 MySQL 工具，只走这些脚本。这是二次开发接入企业内部数据库时最接近官方样例的路径：把受控脚本放进 Skill，把凭据放进用户沙盒环境，而不是把数据库口令写进系统配置让所有智能体共享。

`deep-research` 已在协作章说明。`knowledge-base` 与 `abridge` 分别是知识插件和设备插件的入口说明，随插件登记同步，不应当成普通可选文档删除。新增内置 Skill 时，应模仿这种写法：只描述如何使用已有执行面，并把密钥放在正确的环境边界里。

## 28. 沙盒环境变量与后端环境变量的功能差别

用户经常会把「系统里已经有 SILICONFLOW_API_KEY」理解成「沙盒脚本一定也读得到」。本树的功能边界不是这样。部署环境变量供给 API 与 worker，用于模型供应商初始化、对象存储和数据库连接。用户 Agent 环境变量和沙盒环境变量是另一份，按用户保存，在执行段注入沙盒。`image-gen` 和 `mysql-reporter` 都明确要求脚本读沙盒环境，而不是后端进程环境。验证接口 `POST /api/user/agent-env/verify` 用于检查这类配置，但保存后是否进入已经存在的 Container 执行段，要以文档和实现为准：Container 每个 Run 是临时容器，新的 Run 才会带上新环境；说明文本也写明某些变量保存后仅对新建沙盒或新会话生效。把这一差别当成功能而不是排障细节，可以减少「明明配了密钥却生成不了图」的误判。二次开发编写需要凭据的 Skill 时，必须在正文里写清读取哪一层环境，并在缺失时给出可执行的配置指引。

Cube 与 Container 在用户可感知的功能上也有差别。Container 适合可信代码和本地试用，默认不能上网，临时安装的软件和登录态在执行段结束即消失，工作目录文件仍在。若 Skill 需要访问公网生成图片或查询外部 API，必须意识到默认网络策略可能直接导致失败，这是部署与安全选择，不能假定所有实例都已改成 `bridge`。Cube 保留持久用户环境，更接近「每人一台云端机器」，空闲会休眠，磁盘用量和重建是用户可操作的维护功能。选择哪一种后端，会直接决定 Skill 能不能依赖长期安装的命令行工具。功能文档必须把这个依赖写出来，否则二次开发会把只在 Cube 上成立的流程当成通用能力。

## 29. 图谱功能的权限和运维动作

图谱只支持 Milvus 知识库，不支持只读连接器。开始构建前，文档必须已经解析并完成向量索引，必须选好 LLM 抽取模型，当前账号必须对库有管理权限，Neo4j 和 Milvus 必须可访问。详情页展示抽取、结构写入、向量索引进度和失败块。只读用户可以查看图谱和检索融合结果，但不能配置抽取器、提交构建、重置或修复索引。示例问题可以根据文件列表生成，供检索测试快速检查入口，它不等于经过人工审核的评估基准；要比较检索分数，应使用评估功能并检查参考块和答案。

失败后的功能动作是有顺序的：先保留任务错误和失败块，再分别检查 PostgreSQL 中的块与处理状态、Neo4j 中的实体关系、Milvus 中的图向量，然后才决定重试、修复向量或重置。后台作业成功只表示 worker 完成了编排，三类存储的一致性需要分别回读，不能只看概览状态把所有块都当成成功。这个运维功能属于知识域的管理面，关闭知识运行能力后这些动作与存储会一起停止装配。二次开发不要写一个「忽略失败块、只看作业成功」的同步器。

## 30. 公开协议里与工作台对等的能力

外部系统使用 Public v1 时，应能对等使用工作台里那些已经稳定对外的能力，而不是只发送一行文本。协议支持创建会话和提交后续消息，支持随消息提交附件或图片（图片张数和体积上限与网页相同），支持按回执恢复丢失的提交响应，支持拉取或订阅事件，支持读取队列、Turn、Run、Input 和审计，支持查看协作状态、压缩会话、管理附件、保存或读取交付物。等待、取消和队列控制也在协议范围内。错误与重试必须遵守幂等和状态机，不能把一次超时当作「再发一条新消息即可」。CLI 是这个协议的子集客户端：它能对话和查询知识，但不能在终端完成等待点。自己做业务嵌入时，若场景包含审批或提问，必须实现等待点处理或引导用户回到网页。

协议与网页共用身份作用域：同一用户、同一 APP、同一智能体下的会话互相可见的范围由服务端决定，终端用户 ID 用于隔离被应用代理的最终用户。功能上这意味着一个后台作业系统可以用一把应用密钥，为每个终端用户建立互不干扰的会话。这是多租户能力对外的出口，也是二次开发最应该先对接的功能，而不是去模拟浏览器登录。

## 31. 更多可落地的定制场景

除了资料问答、办公辅助、深度调研和业务嵌入，本树还直接支撑几类更具体的场景。

若要做「对话里出图和出表」：预加载或选择 `chat-widgets`，需要生成图片时再启用 `image-gen`，并在用户沙盒环境中提供生成接口所需密钥，同时确认沙盒网络策略允许访问该接口。交付下载走 `present_artifacts`。不要把模型聊天接口误当成画图服务。

若要做「只读业务库报表」：安装或启用 `mysql-reporter`，让用户在沙盒环境变量中配置自己的 MySQL 连接，限制脚本只读并审查 SQL。更敏感的环境可以把脚本改成只能访问视图或预定义查询。凭据不要放进共享 Skill 正文。

若要做「把飞书或 Notion 里已经存在的资料提供给智能体」：创建对应类型的只读知识库并配置凭据，授权给目标用户，启用知识插件。不要期望在 Yuxi 里再管理一份源文档副本，也不要在这类库上提交图谱构建。

若要做「定时巡检或定时简报」：先准备好智能体、项目和提示词，用定时任务按 cron 和时区触发，审批模式选择默认或始终信任。到点后的执行仍会进入会话历史，结果可在工作台或 Public API 读取。不要另写一个外部 cron 去直接打模型供应商，那样会失去租约、权限和文件边界。

若要做「把个人浏览器或电脑交给智能体」：这是 aBridge 场景，必须完成专用初始化、叠加编排和插件加载，并接受短时委托的安全模型。它不是默认内核，也不可用 Container 联网来代替。

若要做「统一身份登录的企业门户外观」：打开企业 OIDC，配置品牌信息并重新加载，用部门与共享范围映射组织。仍然要保留本地角色和锁定逻辑。Dashboard 留给超级管理员做审计，不要开放给所有登录用户。

这些场景都不要求先裁掉核心功能。它们要求正确选择 Skill、环境变量、知识类型、定时或可选集成，并承认沙盒隔离模型和知识开关会改变能力是否在场。这正是「功能都很核心、用定制而不是堆叠选配来适应场景」在操作上的含义。

## 32. 功能文档收束

至此，Yuxi 的功能已经按域说明：智能体与会话、工具与协作、Skills 与插件、MCP、沙盒与工作区、知识库与评估、图谱、解析、模型、身份治理、外部集成、定时与作业，以及少数真实开关如何改变菜单。内核是一条闭合的工作链路，可选部分在 Compose、环境变量和管理界面上可见，内置 Skill 则示范如何在不增加进程的情况下扩展场景。二次开发应先用检查清单把内核跑通，再按场景打开搜索、连接器、OIDC、设备或自托管解析，并用登记点增加自己的说明和工具。只要不把可选开关写成可以继续无限删除的理由，也不把尚未交付的旧入口或注释掉的供应商写成现成功能，这套功能集就可以作为可定制的私有智能体基座来使用。


## 33. 智能体配置字段如何进入一次运行

创建或编辑智能体时，页面字段并不是装饰性表单，它们会进入 `config_json` 的 Context，并在接收 Input 时冻结到会话或该次输入上。官方配置页 `docs/agents/agents-config.md` 说明，前端不再维护一份独立字段清单，而是由后端 `BaseContext` 的 dataclass 与 metadata 生成配置项描述。`metadata.auth` 只限制谁能修改字段：标为 `admin` 的字段允许管理员和超级管理员修改，标为 `superadmin` 的字段只允许超级管理员修改。普通用户读取有权访问的智能体时仍能读到已保存值，运行也使用这些值；不可修改的字段不进入其编辑表单，后端会拒绝越权提交。`auth` 不提供保密，Context 不得存放凭据。

基础字段的功能含义如下。`system_prompt` 定义角色和行为。`model` 是主模型规格，留空则使用系统默认模型。`tools` 选择可使用的内置工具。`knowledges` 选择可检索的知识库范围，真正开放工具仍要经过知识插件与 MCP。`mcps` 是直接添加到智能体的已启用 MCP 服务器列表。`skills` 选择普通共享和内置 Skill，不含插件入口；个人 Skill 始终可用。`plugins` 是允许按需加载的部署插件 ID 数组，缺省空列表。`preload_skills` 指定从首轮就加载完整说明的普通 Skill 子集。`summary_threshold` 与 `summary_keep_messages` 控制上下文压缩的压力阈值和摘要后保留消息数，阈值单位是 K，缺省 256，约等于 262144 token。`summary_prompt` 与 `summary_tool_result_token_limit` 控制摘要提示词和工具结果预览上限。`max_execution_steps` 是单次运行的 LangGraph 步数上限，缺省 2000，对应 `recursion_limit`；若遇到递归上限错误，应改这个字段并新建会话，已有会话继续用创建时快照。`model_retry_times` 缺省 2。工具审批模式不属于智能体配置，由会话或定时任务选择，省略时为 `default`；历史 Context 里的审批值不参与新会话。

资源字段 `tools`、`knowledges`、`skills`、`mcps`、`preload_skills` 接受字符串 `"all"` 或字符串数组。`"all"` 表示每次运行使用当前用户当时可访问的全部资源，包括之后新增的；`[]` 表示不选；非空数组表示固定范围。新写入拒绝 `null`、未知字符串和非字符串数组成员。创建时省略字段的缺省是：工具、知识库和 Skill 为 `"all"`，MCP、插件和预加载 Skill 为 `[]`。界面「选择全部」保存 `"all"`；逐项勾选即使勾完当前所有项也不会自动变成 `"all"`；「清空全部」保存 `[]`。`plugins` 只接受显式 ID 数组，不支持 `"all"`，未知插件 ID 明确报错，插件入口 Skill 也不能通过 `skills` 或 `preload_skills` 单独选中。MCP 的直接选择与插件引用的 MCP 是两条来源，不会互相删除。预加载候选项限于已选且可访问的共享 Skill；`preload_skills="all"` 只预加载该范围内的完整说明，不额外增加工具。`skills=[]` 时预加载全部仍得到空列表，个人 Skill 仍可按需读正文。

共享智能体保存的是创建者期望的完整选择，每次运行再与当前操作者的可访问资源取交集，运行不会改写保存的选择。例如创建者选了 10 个 Skill，委托管理员只能访问其中 5 个，则委托管理员运行时生效 5 个，但保存名称或模型后仍保留原来的 10 个选择。编辑页只提交改过的字段；通过 API 更新 `config_json.context` 时，省略字段保留原值。修改非空资源列表时，后端会保留当前管理员不可访问的既有引用，并拒绝新增无权引用；保留项维持原相对顺序，新选择追加到末尾。「清空全部」会移除包括不可访问项在内的全部引用。插件没有安装或创建入口，启用插件不会自动创建 MCP 连接，也不会授予数据权限。这些规则合在一起，保证「配置智能体」这项功能既可定制，又不会在委托运行时悄悄扩大权限，也不会因为某管理员看不见某个 Skill 就在保存时把它从共享定义里删掉。

## 34. 命令行功能清单

CLI 是 Public v1 的命令行投影，功能边界比网页窄，但命令本身已经覆盖会话主路径。包通过 `npm` 安装后提供 `yuxi` 可执行文件，`yuxi --version` 输出包版本 `0.1.0` 一级的版本号。连接实例使用 `yuxi remote add`、`use`、`list`、`ping`。登录默认走浏览器设备码，也可用 `--api-key`；`whoami` 与 `status` 查看当前身份和连接，`logout` 退出。对话前可 `agent list` 与 `agent show`，再 `chat --agent <slug>` 进入交互。Thread 操作包括 `thread list`、`show`、`history`、`send`、`watch`，以及用保存的幂等键恢复回执、查看指定 Input 或 Turn、按分页参数拉历史和 turns。多数查询支持 `--json`。文件方面可 `file upload`、`file show`，再在 `thread send` 时用 `--file-id` 附上；图片用 `--image-url` 传 data URL。知识开启时可 `kb list`、`kb files`、`kb query`、`kb open`、`kb find`。排查时应用 `remote ping` 核对 discovery，不要只看终端最后一行判断 Turn 是否成功。

这些命令对应的都是已经在网页和公开 API 中存在的功能，没有另造管理面。二次开发若要做自己的命令行或批处理，应调用同一套 HTTP 协议，而不是解析 CLI 的终端输出。若实例关闭了知识，discovery 会关掉知识子能力，命令应据此失败或隐藏，而不是缓存上一次为真的菜单。

## 35. 上下文压缩与执行步数的功能影响

上下文压缩是会话功能的一部分，会影响用户看到的历史密度和模型后续可用的信息。压力阈值缺省约 26 万 token 量级，达到后会按配置保留若干消息并生成摘要；工具结果也有预览上限，过大的结果落到工作区内部文件，而不是无限塞进上下文。主动压缩接口允许用户或外部系统在会话上触发。压缩失败在 0.8 的修复说明中被强调不能再被当成正常结果。功能上应把压缩理解为「可能改变后续回合所见历史」的操作，重要原文仍应通过知识打开或文件读取回到权威拷贝，而不是相信摘要一定无损。

执行步数上限缺省 2000。过小的历史配置（例如曾经保存为 300）会在长工具循环中触发递归限制错误，需要管理员改智能体配置并新建会话。提高上限只允许更长执行，不能自动修复「智能体在相同步骤上死循环」的提示词或工具设计问题。模型重试次数缺省 2，用尽后应表现为失败，而不是假装成功。二次开发调整这些字段时，必须同步理解它们对已有会话快照无效，只影响新会话或新 Input。

## 36. 知识检索测试与示例问题

检索测试是知识库管理中的日常功能，而不是只有评估模块才有的实验室能力。管理员在库详情中输入查询，可以观察向量初筛、混合结果和重排后的分数变化，并调整持久查询参数。必含词、排除词和完整短语用于收紧结果；最终返回数和召回候选数用于平衡精度与广度；图检索开关用于在需要时引入实体和关系路径。示例问题可根据文件列表生成，适合快速检查入口是否可用，但不能代替带金标的评估集。智能体侧没有「自动把示例问题当回归」的内置调度，二次开发若要做夜间回归，应调用查询测试或评估 API，并自己保存分数趋势。

对只读连接器，检索测试的意义是验证外部凭据和查询是否可用，而不是验证本地分块是否合理。外部源的排序和字段以连接器返回为准。不要期望在只读库上看到与本地 Markdown 切片完全相同的调试面板细节。

## 37. 附件、草稿文件与交付物的用户路径

从用户操作顺序看，文件有三条常见路径，功能上不能混用。第一条是聊天图片：选图后以多模态方式进入消息，受 10 张和 80 MiB base64 总量限制，适合「看图说话」。第二条是附件或工作区文件：上传或从工作区导入后进入 Project Workdir，智能体用文件工具阅读或修改，OCR 工具可生成 Markdown 产物。第三条是交付物：智能体在合适位置写好最终文件后调用 `present_artifacts`，界面出现可预览、下载和保存到个人空间的卡片；对话内图片也可由 widget 直接展示而不先登记交付物。知识库原件走对象存储，不自动变成会话附件。把知识文件「拿进工作区」应使用导入或只读映射，而不是假设智能体默认可写知识桶。二次开发的业务流程若需要「用户上传 → 智能体处理 → 用户下载」，应显式串起附件准备、工具调用和交付物登记，而不是只保存模型文本。

## 38. 权限在功能菜单上的可见差异

同一功能在不同角色眼里菜单不同，这是产品功能而不是前端疏忽。普通用户看到智能体会话、工作区、扩展中心里的 Skills 与个人 MCP 连接、个人设置与密钥；知识库和工具管理入口按管理员要求隐藏或只读；MCP 服务器配置只给超级管理员；Dashboard 只给超级管理员。管理员可以管理部门用户、共享智能体和知识库，但角色天花板仍在。超级管理员可以看集中反馈、改系统选项、管 MCP 和总览。API Key 调用看不到仅供网页的插件提及列表。关闭知识后，所有角色的知识菜单都应不可用或明确提示，而不是显示空库假装正常。二次开发加页面时，必须同时加后端鉴权，并决定它属于哪一层角色，不能只在路由 meta 上写 `requiresAdmin`。

## 39. 与 WeKnora 式广度对照时的功能结论

若把「企业选配很多、不同部分有特别多场景」理解成大量可关可开的子系统，那么本树显示的是另一种功能组织法。Yuxi 也有不少能力名称：协作、评估、图谱、MCP、OCR、OIDC、设备、观测、定时、Dashboard。但它们不是并列的一级产品线，而是同一内核上的出口或登记项。能够整段拿掉的主要是知识运行面；能够替换的是沙盒隔离和解析引擎；能够后装的是登录、设备、搜索和观测。智能体配置字段再多，也仍然进入同一次 Run 的 Context。内置 Skill 再丰富，也不增加 Compose 服务。因此，功能文档支持这样的判断：Yuxi 适合在自己的场景上二次开发，而不是先做一次大型裁剪；同时也必须承认 no-knowledge、MinerU profile、Cube、aBridge 等开关是真实的，不能为了强调「都很核心」而否认它们会改变菜单。诚实的功能图景是「内核闭合、出口丰富、开关少数且可见」。


## 40. Skill 的安装、版本和个人来源

Skill 管理在功能上分成共享治理和个人安装两条线，入口都在扩展中心，接口同时挂在 `/api/system/skills` 与 `/api/skills`。共享侧可以查看内置列表并触发同步，读写某个 slug 的内容、文件树和单文件，创建版本、恢复历史版本或删除指定版本，导出整包，调整共享范围和启用状态，以及批量删除。内容保存使用修订值拒绝过期覆盖。个人侧可以准备安装草稿、确认安装、读取或删除个人 Skill 文件。远程来源提供列表、搜索和准备安装，但有来源限制，不是任意 URL 都可以变成 Skill。安装草稿可被取消。个人 Skill 始终对所属用户可用，不必写进智能体的 `skills` 列表。

这些功能让团队可以沉淀可复用的操作说明，又允许个人安装自己的技巧，而不把代码插件的发布权交给普通用户。二次开发新增团队级流程，应优先写成共享 Skill 并设置读范围；只有需要改运行时代码时才走部署插件登记。恢复历史版本不会改写已经开始的 Run 所用快照。导出用于备份或在受控前提下迁移到其它实例，但不能替代 Schema 与数据目录的整体备份。

## 41. 首次运行、登录和企业登录

产品安装后的第一个功能是首次初始化。`check-first-run` 告诉界面是否还没有超级管理员，`initialize` 在锁保护下创建首位超管。完成前不能把业务会话当成已经可多用户使用。之后的本地登录使用用户名与密码，失败会触发账号锁定和 IP 限速。用户可修改资料与密码，管理员可代为管理普通账号。这些是内核功能。

企业登录是可选功能。部署打开 `OIDC_ENABLED` 并填写 issuer、客户端和回调后，登录页出现第三方入口。Yuxi 要求 discovery 的 issuer 与配置精确一致，使用指定算法的 JWKS，校验 ID token 受众和 UserInfo 的 subject。生产模式拒绝 HTTP 的 issuer、回调和协议端点，浏览器到站点、到认证中心以及 API 到认证中心都必须是 HTTPS。可选范围缺省包含 `openid profile email`，必须含 openid。`OIDC_AUTO_CREATE_USER` 缺省为真：已验证但尚无映射的外部身份会自动开通普通用户；关闭则拒绝未预先开通的身份。外部登录仍受本地锁定、删除和人类用户类型检查。公网只有 HTTP 时应保持企业登录关闭，登录页会隐藏第三方区域。回调路径有专门的日志脱敏。二次开发对接认证中心时，应按这份契约注册客户端，而不是降低校验去迁就不完整的提供商实现。

Yuxi 作为签发端是另一项可选功能，主要服务于 aBridge 一类静态客户端，需要独立 RSA 密钥和显式登记，不是给普通终端用户替代企业认证中心的方案。

## 42. 可选观测在功能上能做什么

Langfuse 接入后，可以把一轮工作中各段 Run 的模型调用、工具调用、耗时和错误放到同一条 Trace 里，按用户 uid、会话 thread_id、回合 turn_id、执行 run_id 和智能体筛选。对话中的点赞或点踩仍保存在 PostgreSQL，超级管理员可以从集中反馈打开所属 Turn 的 Trace。会话调试面板里的跳转只接受超级管理员的产品 JWT，拒绝所有 API Key。Langfuse 项目本身的访问权限由 Langfuse 执行。没有配置公钥和密钥，或显式设置关闭时，聊天和 AgentRun 仍按本地链路运行。环境变量改完需要重建 API 和 worker。密钥不能写入仓库、Agent 环境或公开日志。功能上应把它当成排查和复盘工具，而不是业务结果的存储，也不能用它取代 Dashboard 或数据库中的反馈记录。

用量统计若要对接到网关，属于另一项可选功能，需要按文档配置请求头与验签，并且尊重不可信供应商的用量不会被累计这一限制。不要把两项观测混成「系统已经自带完整账单」。

## 43. 分块预设和 URL 导入的使用边界

分块预设是入库功能里需要管理员理解的选择，而不是开发开关。`general` 适合大多数普通文档，按分隔符和长度切分。`qa` 优先抽取问答结构，适合 FAQ 和题库。`book` 强化章节标题与层级合并，适合教材和长手册。`laws` 按法条层级组织，适合法规和制度。`semantic` 利用嵌入和聚类做语义切分并增强标题上下文，依赖可用的嵌入能力，成本通常更高。`separator` 命中分隔符即切分，只在超长片段内继续按长度切，适合结构非常规则的文本。库级默认可以按文件或单次请求覆盖。选错预设不会让系统拒绝入库，但会直接影响检索测试和评估分数。二次开发若有固定文类，应在创建库时写死合适的预设，而不是让每次上传都临时选择。

URL 导入把网页变成知识库文件，但默认并不开放到整个互联网。未配置白名单时该能力关闭；环境变量可提供缺省域名列表，页面保存的安全设置优先，空列表不会回退到环境变量。导入弹窗会显示未启用、域名不允许、内容限制或抓取失败的原因。进行中的抓取沿用开始时读取的列表。只改环境文件仍需按部署流程重建 API。这项功能适合纳入「官方文档站点或内网 Wiki」，不适合当成通用爬虫。与网络搜索工具相比，URL 导入的结果会进入知识库状态机并长期索引，搜索工具只服务当轮对话。

## 44. 就绪状态作为功能入口

对使用者来说，「系统是不是已经可以用」是一个功能问题。健康接口只表示 API 进程活着，就绪接口还要求启动完成、数据库和 Redis 可用、存在健康的 worker 租约。discovery 再告诉客户端知识是否打开、CLI 能做什么。首次初始化完成后，打开工作台创建会话、在工作区写一个测试文件、如需要再上传一篇文档做检索测试，才算把内核功能走通。就绪不能证明模型密钥有效、沙盒能执行或知识已索引。二次开发的探活和用户提示应区分这几层，避免在只通过健康检查时就宣布「问答已经可用」。

## 45. 终章：如何用这套功能做自己的产品

如果要把 Yuxi 当作二次开发基座来做出自己的产品，功能上的工作顺序可以收成一句：先让内核闭环在自己的组织里跑通，再只打开场景需要的开关，最后用 Skill、工具和公开协议包上自己的业务外壳。内核闭环是指：有超管和部门用户，有可用的聊天模型，有一种沙盒后端，能在工作区看到智能体写下的文件，会话、审批和交付物可理解。若业务依赖企业内部资料，再打开默认知识面，选对分块和 OCR，配好嵌入模型，用共享范围和知识插件把检索交给正确的人。若业务依赖外部系统，用分级 API Key 和 Public v1 嵌入，而不是改前端。若业务依赖已有账号、个人设备或深度观测，再打开对应可选集成。

沿这条顺序前进，不需要先争论「哪些模块是冗余的」。源码已经把冗余降到少数可见开关，并把场景差异放到配置和说明书里。功能很多，但它们是同一条链路的不同出口；出口可以选用，链路本身不宜再拆。这就是本功能文档对 Yuxi 的结论，也是与那种靠大量选配去覆盖企业场景的产品之间，最重要的使用差别。


## 46. 网页反馈与改进线索如何采集

网页工作台允许用户对已经结束的一轮回答点赞或点踩。这是明确的 Web 产品功能，只接受产品 JWT，拒绝 API Key，Public API 不提供反馈路由。评价只能针对自身产品会话中的终态 Turn，并且 `run_id` 必须等于该 Turn 的结果 Run，还要有明确的最终助手输出。等待中、中间 Run 或没有最终回答的错误会得到 409，未知或越权目标得到 404。提交内容是完整的当前值，包含 `run_id`、`like` 或 `dislike`，以及可选原因，原因去掉空白后最多 2000 字。提交后返回记录 ID。撤销评价时要带上 `run_id`，重复撤销仍返回成功；智能体自己写下的改进标记不会因为用户撤销评价而被删掉。用户可以分页查看本会话中来自用户或智能体的记录，按最多 100 个 run_ids 过滤。每个 Run 只保留一份当前用户评价，重复写入不增行，并发修改保留最后提交值，不保存点击历史。归档会话保留记录，删除会话后查询会隐藏这些记录。

超级管理员通过系统反馈接口集中查看，可按智能体、来源和评分筛选，普通管理员、智能体管理者和所有 API Key 都被拒绝。列表不返回原始对话、运行清单或私有 Skill 元数据，也不因此扩大原会话、审计或文件权限。打开 Langfuse 的跳转按反馈定位 Turn，已删除会话的反馈返回 404。保存反馈只完成采集，后续复盘和更新 Skill 需要独立流程。智能体侧的 `mark_for_improvement` 与用户评价是两条来源，可以同时存在。二次开发若要在自己的界面里做评价，不能走 Public API，除非另行扩展协议；当前实现就是把评价留在 Yuxi 网页。

## 47. 默认智能体、按 Skill 创建和资源所有权转移

产品需要一个「用户打开工作台时首先用谁」的功能。管理接口可以把某个智能体设为默认，目录里也可以读取当前默认项。按 Skill 创建智能体则是把一份操作说明快速变成可运行配置的入口，适合从已有 Skill 出发做场景定制，而不必从空白表单开始。详情接口返回 `can_manage`、`can_run`、`can_share` 和 `can_transfer`，界面按这些能力显示操作。共享资源的所有权可以由具备权限的管理者转移到另一用户，系统接口 `PUT /api/system/resources/{kind}/{resource_id}/owner` 提供这一动作。转移的是治理关系，不会自动改写已经冻结的会话配置，也不会把原作者的私有对象一并搬走。二次开发在做「离职交接」或「团队负责人变更」时，应使用这一正式转移，而不是修改数据库里的 `created_by` 字段。

隐式项目与可选项目也影响「用户怎么开始一次工作」。尚未显式挑选目录时，系统可以有一个可为空名称的隐式项目来承接会话和工作区文件；用户在工作台或项目列表中明确选择后，项目变为可选且通常具有名称。把文件任务交到错误的目录，多半是因为会话绑定的项目不是用户以为的那一个。工作台查询参数里的 `project_id` 正是为了把这次对话钉在正确的 Workdir 上。二次开发嵌入会话时，也应显式选择项目，而不是依赖隐式项目的当前状态。

## 48. 各文档类型在入库时的功能差异

同样是「上传到知识库」，不同类型进入检索的路径并不相同，使用者需要知道差异，才能判断该不该开 OCR、该不该打 ZIP 包。纯文本、Markdown、JSON、CSV 走文本解析。HTML 默认要能找到正文引用的本地图片，否则整篇失败，除非显式只要文字。Word、PPT 和现代 Excel 由 Docling Slim 提取正文与图片，老的 `.xls` 走另一套表格保留。PDF 若关闭 OCR 只读文本层，扫描件会得到空或极弱的结果，必须启用 OCR。图片必须启用 OCR。ZIP 必须包含 UTF-8 Markdown，优先 `full.md`，否则取路径排序后的第一个 Markdown，并按完整路径提取引用资源；绝对路径、父目录穿越、重复项、符号链接或缺失图片会使整个结果被拒绝。空白 Markdown 可以是合法的空结果，但缺少 Markdown 不行。MinerU 返回的归档也遵循同一套规则。功能上这意味着：把扫描合同直接当「关闭 OCR 的 PDF」上传，不会得到可用知识库；把网页另存为不带图片的 HTML 却不打开 `html_text_only`，会解析失败。二次开发做批量入库时，应按类型准备参数，而不是只用一个全局开关对付所有文件。

## 49. 功能文档的使用说明

本文与架构文档分工如下：架构回答系统如何分成进程、表和登记点；本文回答用户和二次开发者能够做什么、从哪进、是否可关、如何配置、以及遇到限制时该怎么理解。二者都只依据本树源码和仓库内官方文件，分析期间没有启动 Compose，也没有把任何密钥写入文档。版本上仍须分清官方 `v0.8.0` 标签、当前 `main` 提交 `47e4e5a` 和包版本字符串 `0.8.0`。若后续要按标签复现发行行为，应以该标签树重新核对功能，不能假定与本树完全一致。把这两份文档对照阅读时，应以源码路径和接口名为准，而不是以市场通稿式的模块口号为准。


## 50. 会话检索、置顶、归档和标题

工作台左侧或会话列表提供一组组织个人工作的功能，虽然不起眼，却属于内核体验。会话可以按智能体或关键字搜索，可以置顶，可以归档而不立即删除历史。标题通常由运行时自动生成，失败或超时时回退到可读名称，不再把协议标记或内部 ID 写进标题。打开会话时会记录最后查看的顶层 Run，便于回到上次看到的位置。这些操作改变的是会话投影和列表排序，不会改写已经完成的 Turn 结果。归档后反馈记录仍然保留，但按删除规则查询时会被隐藏。二次开发做自己的会话列表时，应调用公开的搜索、查看和归档接口，并理解归档与删除是不同的生命周期，不要把归档当成已经可以回收工作目录的信号；回收工作目录属于删除项目时的规则，而且仍会拒绝存在活跃回合或待处理输入的项目。

把列表组织、反馈采集、默认智能体、文档类型差异和首次登录连在一起看，日常使用 Yuxi 并不需要先理解全部登记表。使用者先初始化身份，选好默认智能体和项目，在工作台里提问、上传或交付文件；管理员再按组织配置共享范围、模型、知识库和可选集成。功能深度藏在这条日常路径的每个步骤里，而不是藏在一排需要事先勾选的企业模块开关上。这与本文开头的判断一致：适合二次开发去定制场景，而不是先做大规模裁剪才能开始工作。


## 51. 开放文档与 Swagger 的关系

部署成功后，开发环境可以在 API 进程上打开 OpenAPI 页面，查看当前实例实际挂载的路由和模式。功能文档按域归纳这些路由，但不能代替实例上的 Schema：知识关闭时，知识相关路径不会装配，Swagger 里也就不应再把它们当成可调用接口。字段级权限、错误码和请求体以当时运行的应用为准。二次开发联调时，应先看 discovery 和就绪，再以当前实例的 OpenAPI 为准实现客户端，并以本文理解这些接口在产品上的含义和限制。版本字段来自 Python 包元数据，客户端兼容性还要看 Public v1 的语义，而不是只比较一个三位版本号。若官方稍后打出与本 `main` 树不同的新标签，应以新树重新核对，不要假设功能面保持静止。

至此，功能清单已经覆盖从开机初始化到日常会话、知识治理、协作工具、内置 Skill、公开协议和可选集成的主要入口。内核闭环仍然是智能体、默认知识检索、权限和沙盒工作区；少数开关改变的是菜单是否在场，而不是这条闭环能不能被称为一个完整产品。


对于只想验证「这套系统是否已经按核心功能工作」的人，不必把本文所有章节都做成检查项。只需确认：超级管理员已经初始化，默认模型可以对话，选定的沙盒能在工作区留下文件，如需知识则至少有一个已索引且已授权的 Milvus 库能在检索测试中命中，智能体已启用知识插件并且当前用户对库有读权限。通过这组最小验证后，再按自己的场景增加搜索、连接器、定时、OIDC 或设备。最小验证失败时，应先查就绪、模型配置和沙盒后端是否与 Compose profile 一致，而不是去关闭更多模块。Yuxi 的功能用法从这里开始，而不是从一份冗长的选配清单开始。


如果最小验证已经通过，却仍觉得「功能太多不好用」，应区分两种情况。一种是界面同时展示了知识、扩展和治理入口，这是默认完整交付的结果，可以通过权限和角色让普通用户只看到工作台与工作区，而不必关闭知识进程。另一种是确实不需要检索和图谱，这时才使用 no-knowledge 叠加，并让所有客户端重新发现能力。前者是体验裁剪，后者才是运行面裁剪；二者都不应理解成产品内核还可以继续拆薄。把体验裁剪和运行面裁剪分开处理，二次开发才不会误伤那条已经不可再瘦的工作链路。


同样，觉得「某些能力好像可有可无」时，应先问它是不是某条出口，而不是不是内核本身。评估、图谱浏览、Dashboard、CLI 和 Langfuse 都是出口：不用它们，会话和权限仍然成立；但若为了精简而拆掉会话队列、工作目录或默认知识检索，产品就不再是文档所描述的 Yuxi。二次开发可以不使用某个出口，不宜删除出口所依赖的那条主链。

源码路径、接口名和配置项始终是核对依据；若发现本文与当前树不一致，应以源码为准修正文档，而不是反过来要求源码迁就文档中的概括。
